# Hashed public profile URLs + Identity Manage page restructure (item 17)

**Type:** Feature / change

## Summary
Two related changes: public profile URLs no longer expose the raw ASP.NET Identity Guid, and the
Identity "Manage account" area (previously never scaffolded at all - flagged as a real unknown
during this session's planning) now exists with 2FA/Personal-data removed and a link to the
current user's own public profile added.

## Techniques
- **`IdentityStage`'s `id.Modules` is data-driven from the spec** (not hardcoded in C#) - just
  added `Account.Manage._Layout;._ManageNav;._StatusMessage;.Index;.Email;.ChangePassword` to
  `identity.modules` in the fixture. Deliberately did NOT include the 2FA/PersonalData/
  ExternalLogins/SetPassword page group - those pages simply don't exist, matching Stefan's
  "remove 2FA and personal data" ask at the scaffold level, not just the nav level.
- **New `ProfileHash` static helper** (`templates/models/profile_hash.sbn`, emitted to
  `Infrastructure/ProfileHash.cs`): `SHA256(userId)` truncated to 12 hex chars - deterministic, not
  stored anywhere, `ProfilesController.Public` materializes all user IDs and compares hashes
  in-memory (the hash function is plain C#, not SQL-translatable, so it can't run inside an EF
  query). Not cryptographic protection (technically brute-forceable over a small user set) -
  the goal is only to stop the raw Guid appearing in the address bar, which was the actual ask.
  Every existing "link to a user's public profile" call site updated to wrap the ID:
  `catalogues_public.sbn`, `posts_details.sbn`, `product_details.sbn`,
  `user_profile_content_partial.sbn` (x2 - Followers/Following lists).
- **New transform** `RestructureManageNav`: removes the scaffolded `_ManageNav.cshtml`'s
  TwoFactorAuthentication/PersonalData `<li>`s (their pages were never scaffolded, so the stock
  nav's links to them would 404) and injects a "Публичен акаунт" link to
  `Profiles/Public/{ProfileHash.Of(current-user-id)}`, plus a `UserManager` injection (only
  `SignInManager` is scaffolded by default).

## Three real bugs caught and fixed via live regeneration (not guessed)
1. **Blind residue-map corruption of C# identifiers.** The BG translation map's `"Email":
   "Имейл"` (and `"Password"`) blindly string-replaced INSIDE C# type/property references that
   happen to contain those words as substrings - `EmailModel` → `ИмейлModel`, `ManageNavPages.Email`
   → `ManageNavPages.Имейл`, `ChangePasswordModel` → `ChangeПаролаModel` - all compile errors. These
   collisions were never triggered before because Manage pages had never been scaffolded until this
   session. There's no reliable text-only way to distinguish "translatable prose" from "bare C#
   identifier reference" on the same code line, so excluded the whole `Manage/` subtree from the
   blind map rather than attempt fragile heuristics - it's new-to-this-session scaffolding, not a
   regression in previously-working translated pages.
2. **Two separate `_ViewImports.cshtml` layers needed the new `Infrastructure` using**, not one:
   the per-MVC-area ones (`Areas/{Admin,Client}/Views/_ViewImports.cshtml`, generated by dps-nn
   itself) AND the Razor Pages ones under `Areas/Identity/Pages/` (scaffolder-generated, entirely
   separate convention, `_ManageNav.cshtml` needed the top-level one specifically since Razor's
   `_ViewImports.cshtml` cascades down the folder tree).
3. **Pipeline stage ordering**: `ProfileHash.cs` was originally emitted in
   `EmitControllersViewsStage` (a later stage), but `IdentityStage` (earlier) scaffolds and
   BUILD-CHECKS `_ManageNav.cshtml`, which references `ProfileHash` - the type didn't exist yet at
   that build-check point. Moved the emission into `IdentityStage` itself, before the scaffold call.
